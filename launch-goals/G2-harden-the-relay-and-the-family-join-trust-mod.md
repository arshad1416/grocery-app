**2. Family invites are self-signed, so anyone can forge one.** At `server.js:611` the invite signature is verified with `verifyEd25519Signature(invitePayload, signature, inviterDeviceId)`. The helper's parameters are `(message, signature, publicKey)` (`server.js:396`), so the third argument is the public key — and `inviterDeviceId` comes out of the invite itself, parsed at line 586. An attacker generates their own keypair, sets `deviceId` to their own public key, picks any `familyId` they like, signs the payload, and enrolls. The signature is valid; it just proves nothing.

The relay has no out-of-band knowledge of who belongs to a family, so build a membership registry: the first enrollment for a previously unseen `familyId` records the inviter's signing key as the founding member, and every later enrollment for that `familyId` requires the invite's signer to be a key already recorded for it.

Understand the ceiling on this fix before you build it, because it determines what you must hand off. `/enroll` receives the joiner's `deviceToken`, which the client documents at `GroceryApp/src/identity/enroll.ts:34` as the device's base64 box public key and passes as `getDeviceId()` from `PairingScreen.tsx:121` and `invite-link.ts:82`. Invites, however, are signed with a *different* key — the Ed25519 key derived at `GroceryApp/src/identity/family.ts:111-112` via `crypto_sign_seed_keypair`. The relay never learns any enrolled device's Ed25519 public key and cannot derive it from the X25519 one, so your registry can only ever hold founding signers. The consequence is real and you must say so out loud: until the client also sends its signing key at enrollment, only the founding device can issue invites that this relay will accept. Implement the server side, write the required client-side counterpart into the notes naming `GroceryApp/src/identity/enroll.ts:39-54` as the file, and do not implement it yourself.

A correct implementation already exists at `extract/extract-server.js:168-192`: `collectBody(req, maxBytes)` pre-checks `content-length` at line 170, counts bytes as they arrive, and calls `req.destroy()` at line 181 the moment the cap is exceeded. The point is one implementation to audit instead of seven, which you do not get by copying it.

**6. `GET /stats` is unauthenticated and leaks the whole tenant list.** At `server.js:688-718` it returns every active `familyId` as an object key plus a 12-character prefix of each connected device's id at line 697 — a stable fingerprint. `server.js:505` sets `Access-Control-Allow-Origin: *` for every response on this server, so any web page can read it. This is marked a launch blocker.

Authenticate it with the mechanism the relay already uses for `POST /relay/request-token`: `Authorization: Bearer <relayToken>` looked up in `enrolledDevices`, at `server.js:1388-1396`. That pattern fails closed by construction, which an environment-variable secret does not — `req.headers.authorization === process.env.STATS_TOKEN` is wide open on a default deploy where the variable is unset, so do not write that. Remove the per-family map and the device-id prefixes from the payload entirely rather than merely gating them; aggregate counters are fine. **7. Blind-RSA tokens become re-spendable after 24 hours.** `tokens/used-tokens-store.js:18` sets `DEFAULT_TTL_MS = 86_400_000`, and the prune at line 122 drops any spent-token record older than that, measured from when it was first spent.

Before you touch this, understand the constraint that decides the fix, because it is easy to get wrong: the token format is `v2.<base64>` where the base64 decodes to exactly 288 bytes — a 256-byte RSA signature followed by a 32-byte nonce (`pool/pool-server.js:89-120`), verified at line 273 as signature-over-nonce only. There is no expiry, no issuance timestamp and no epoch identifier in the token, and the nonce is client-chosen and blinded so the issuer never sees it. The verifier therefore has no way to reject a token for being old, which means raising the TTL fixes nothing — any finite TTL leaves a double-spend window. Only two designs close it: keep the spent set permanently but compact it by storing a hash of the token rather than the token string, or introduce issuer-key epochs so an out-of-window token fails signature verification and the TTL can be pinned to the epoch length. Pick one and write down in the notes why.
